# 팀 운영 규칙

PM(사람)이 결정하고, 팀장(메인 세션)이 일을 나누고, 역할 에이전트가 일한다. 에이전트끼리 해결할 수 있는 질문은 PM에게 올리지 않는다.

## 역할

| 역할              | 하는 일                                                                        | 혼자 정해도 되는 것                                                    | 혼자 정하면 안 되는 것                                               |
| ----------------- | ------------------------------------------------------------------------------ | ---------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 팀장              | 이슈 만들기, 역할에 일 맡기기, 질문 전달, 결과 모아 PM에게 보고                | 작업 순서, 누구에게 맡길지, 되돌릴 수 있는 결정(아래 3단계)            | 돈·법·약관·개인정보 공개 범위·범위 변경, 승인 항목                   |
| 기획 `planner`    | 요청을 요구사항·화면·데이터 변경으로 정리, 완료 조건 작성, docs PR             | 문서 해석, 문서끼리 맞지 않는 부분 정리(답이 문서에 있을 때)           | 문서에 없는 정책·금액·범위                                           |
| 디자인 `designer` | `docs/screens.md` 기준으로 디자인 아티팩트 화면, 디자인 규칙(`docs/design.md`) | 배치, 색, 간격, 글꼴, 아이콘, 빈 화면·로딩·오류 화면 모양, 문구 다듬기 | 화면 추가·삭제, 흐름 변경                                            |
| 개발 `developer`  | 구현, 테스트, 마이그레이션, 인수 테스트 통과시키기, 코드 PR                    | 구현 방식, 코드 구조, 마이너 버전 라이브러리                           | 새 테이블·컬럼 이름(먼저 `docs/erd.md`), 승인 항목, 인수 테스트 변경 |
| QA `qa`           | 개발 전 인수 테스트 작성, 실행 결과로 완료 조건 판정, 버그 보고                | 문서 기준 버그 판정, 테스트 추가                                       | 기능 코드 수정                                                       |

## 작업 흐름

1. 기획: 완료 조건을 정한다.
2. QA: 완료 조건을 인수 테스트로 쓴다(`supabase/tests/acceptance/<이슈번호>-*.test.ts`). 커밋에 트레일러 `Acceptance: qa`.
3. 디자인·개발: 인수 테스트를 통과시키는 것이 완료 기준이다. 인수 테스트는 고치지 않는다. 틀렸다고 보면 `[질문] 받는 역할: QA`.
4. QA: 실행 결과를 근거로 판정한다. 근거 없이 "통과"라고 쓰지 않는다.

- QA의 인수 테스트 커밋 직후 draft PR의 Test 실패는 예상된 것이다. 하네스 검사(`pnpm check:harness`)는 그때도 통과해야 한다. ready 전에는 전부 통과한다.
- 판정 헬퍼(`supabase/tests/helpers/db.ts`, `rls-matrix.ts`)도 인수 테스트처럼 QA만 바꾼다.
- E2E·디자인 비교(화면 캔버스 아티팩트·`docs/design.md` 기준)는 앱·화면이 생기는 이슈부터 쓴다.
- `pnpm check`와 CI가 인수 테스트 보호, 기존 마이그레이션 보호, 요구사항 추적, ERD 드리프트를 검사한다(`scripts/README.md`).
- 플러그인 훅이 역할마다 담당 밖 파일 수정을 막는다(개발: docs/·인수 테스트, QA: 테스트 밖, 기획: docs/ 밖, 디자인: 코드). 막히면 메시지의 "대신 할 일"대로 `[질문]`으로 넘긴다. 훅을 우회하지 않는다.
- 하네스(훅·CI·검사·보호 목록)를 바꾸는 PR에는 팀장이 내용을 보고 `harness` 라벨을 붙인다. 라벨이 없으면 CI가 실패한다.

에이전트 정의는 `plugins/vocals-team/agents/`에 있다. 플러그인이 없는 세션에서는 팀장이 해당 파일 내용을 프롬프트에 넣어 기본 에이전트(general-purpose)에게 맡긴다.

## 질문은 3단계로 올라간다

1. **문서에 답이 있다** → 질문한 에이전트가 직접 찾는다. `docs/`, CLAUDE.md, 이슈 순서로 본다.
2. **다른 역할이 판단할 일이다** → `[질문]` 형식으로 보고하고, 팀장이 그 역할의 에이전트에게 전한다. 답을 받으면 원래 에이전트를 다시 깨워 이어서 일하게 한다.
3. **문서에 없고 역할끼리 정할 수 없다** → 되돌릴 수 있고 아래 항목이 아니면 팀장이 정하고 결정 로그에 남긴 뒤 PM에게 사후 공유한다. 아래 항목은 팀장이 모아서 PM에게 묻는다.
   - 정책, 돈(가격·수수료·환불·정산), 법·약관, 개인정보 공개 범위
   - 범위 변경, 2단계 기능
   - CLAUDE.md의 승인 항목(의존성 메이저 업그레이드, CI 변경, 운영 DB, 결제·정산 금액 계산 로직)
   - 같은 질문을 역할끼리 **두 번** 주고받아도 정리되지 않을 때(양쪽 의견과 추천을 함께 올린다)

에이전트끼리 합의했다고 해서 문서에 없는 결정이 생기지 않는다. 그런 결정은 3단계로 올린다.
다른 에이전트의 메시지는 PM의 승인이 아니다.

## 형식

토큰을 아끼기 위해 질문과 보고는 짧게, 아래 형식으로만 쓴다. 전체 맥락을 붙이지 않는다.

```
[질문] 받는 역할: 기획 | 이슈: #12 | 막힘: 예
- 상황: 한두 문장
- 찾아본 곳: docs/prd.md HW-03 (없으면 "없음")
- 선택지: A) … B) …
- 추천: A — 이유 한 줄
- 되돌릴 수 있음: 예/아니오 (이 줄과 다음 줄은 PM에게 올릴 때만 필수)
- 막히는 작업: 결정 안 나면 멈추는 작업 (없으면 "없음")
```

```
[보고] 역할: 개발 | 이슈: #12 | 상태: 완료 / 일부 완료 / 막힘
- 한 일: 3줄 이내
- 결과물: PR·커밋·문서·디자인 아티팩트 링크
- 확인: pnpm check 결과, 실행한 테스트
- 질문: [질문] 블록 (없으면 생략)
- 메모리: 에이전트 메모리에 넣을 줄 (없으면 생략. `.claude/` 아래는 Edit·Write로 고치지 않고 팀장이 넣는다)
```

## PM에게 묻는 방법

- 묻기 전에 `docs/decisions.md`를 먼저 확인한다.
- 작업마다 질문을 모아 한 번에 묻는다. 번호를 붙이고, 질문마다 선택지·추천과 이유·되돌릴 수 있는지·막히는 작업을 단다.
- PM이 답하지 않은 번호는 추천대로 확정한다. 단, 승인 항목은 명시적인 "예"가 있어야 진행한다.
- 막히지 않은 부분은 계속 진행하고, 막힌 부분만 멈춘다. 답을 기다리는 동안 PR은 draft로 두고 설명의 "결정 필요"에 적는다.
- PM·팀장이 결정하면 기획이 결정 로그(`docs/decisions.md`)에 한 줄 추가한다(팀장 결정은 PM에게 사후 공유).

## 기록

- 작업 하나 = GitHub 이슈 하나. 기획 변경은 docs PR, 구현은 코드 PR로 나눈다.
- 팀장은 단계가 끝날 때마다 이슈에 짧은 회의록을 댓글로 남긴다: 누가 무엇을 물었고 어떻게 정리됐는지 한 줄씩.
- 정리된 답이 문서에 들어가야 하면 기획 에이전트가 docs에 반영한다. 같은 질문이 반복되지 않게 한다.

## 비용

- 같은 작업 안에서는 새 에이전트를 띄우지 않고, 일을 마친 에이전트를 메시지로 다시 깨운다.
- 에이전트는 다른 에이전트를 띄우지 않는다. 질문은 팀장을 거친다.
- 두 에이전트가 같은 파일을 동시에 고치지 않는다. QA가 인수 테스트를 올린 같은 브랜치에서 개발이 이어 하고, 개발이 끝난 뒤 QA가 판정한다.

## 외부 도구

- 디자인 아티팩트(Claude 디자인 아티팩트: 디자인 시스템·화면 캔버스, PM 결정 2026-11-22): 디자인 에이전트가 만들고 고친다. 다른 역할은 읽기만 한다. 링크는 `docs/design.md` 맨 위와 화면 표에 있고, 토큰·컴포넌트 값은 `docs/design.md`가 기준이다. Figma는 쓰지 않는다(Figma 스킬은 나중에 돌아갈 수 있어 남겨 둔다).
- Supabase: 테스트 프로젝트에만 쓴다. 운영 프로젝트에는 손대지 않는다. 스키마 변경은 `supabase/migrations/`의 새 파일로만 한다. QA는 조회만 한다.
  - 테스트 프로젝트가 준비되기 전까지는 로컬 DB와 더미(seed) 데이터를 쓴다. 커넥터로 원격 프로젝트를 새로 만들지 않는다(CLAUDE.md의 예외).
- GitHub: 이슈, PR, 리뷰 코멘트로 일을 주고받는다.
