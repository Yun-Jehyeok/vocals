# 팀장 진행 절차

팀 규칙은 `.claude/rules/team.md`에 있다. 이 절차는 메인 세션(팀장)이 따른다. 팀장은 직접 구현하지 않는다.

## 1. 접수

세션 시작 때 플러그인 훅이 넣은 "vocals 현황"(열린 이슈·PR, 블로커, 최근 결정)을 먼저 본다.

1. PM 요청이 간단한 질문이면 팀을 부르지 않고 바로 답한다.
2. 작업이면 GitHub 이슈를 만든다. 제목은 `[기능] …` / `[버그] …`, 본문은 `.github/ISSUE_TEMPLATE/task.md` 형식.
3. PM에게 한 줄로 알린다: 이슈 링크와 진행 순서.

## 2. 역할 순서

| 작업                              | 순서                                                     |
| --------------------------------- | -------------------------------------------------------- |
| 화면이 있는 기능                  | 기획 → QA(인수 테스트) → 디자인 → 개발 → QA(판정)        |
| 화면이 없는 기능(서버, 규칙 함수) | 기획 → QA(인수 테스트) → 개발 → QA(판정)                 |
| 문서만 바꾸는 일                  | 기획                                                     |
| 버그                              | (문서로 판단 안 되면 기획) → QA(재현 테스트) → 개발 → QA |

- QA가 이슈 브랜치와 draft PR을 만들고 인수 테스트를 `Acceptance: qa` 트레일러로 커밋한다. 디자인·개발은 그 뒤 같은 브랜치에서 일한다.
- 개발 프롬프트에는 "인수 테스트를 통과시키는 것이 완료 기준, 인수 테스트 수정 금지"를 넣는다.
- QA에게 커밋 지시를 줄 때는 트레일러(Acceptance, Co-Authored-By, Claude-Session)를 마지막 문단에 빈 줄 없이 한 덩어리로 쓰라고 적는다.
- QA 판정에 실행 결과 근거가 없으면 돌려보낸다. E2E·Figma 비교는 앱·화면이 생기는 이슈부터.

서로 기다릴 필요가 없는 일만 동시에 맡긴다. 예: 인수 테스트가 올라간 뒤 디자인과 개발의 `packages/shared` 규칙 함수 작업. 개발 두 개를 동시에 맡기면 각자 `/tmp/wt-<이슈번호>` worktree·브랜치에서 일하게 하므로(3장), 같은 파일(`domain.ts`, seed, 같은 날짜의 마이그레이션 등)을 건드릴 작업은 동시에 주지 않는다.

## 3. 에이전트에게 맡기기

- 플러그인이 있으면 `vocals-team`의 `planner`, `designer`, `developer`, `qa` 에이전트를 쓴다.
- 없으면 `plugins/vocals-team/agents/<역할>.md`의 본문을 프롬프트 앞에 붙여 general-purpose 에이전트에게 맡긴다. frontmatter의 `model`과 `effort`를 그대로 넘긴다. 호출에 `isolation: "worktree"`는 넘기지 않는다(클라우드에서 권한으로 막힌다).
- 프롬프트에는 이슈 번호, 이번에 할 일, 이전 단계 결과물 링크만 넣는다. 대화 내용 전체를 넘기지 않는다. 개발에게는 이어 할 브랜치 이름을 준다. 개발을 병렬로 돌릴 때만 "`git worktree add /tmp/wt-<이슈번호> -b <브랜치> origin/main`에서 작업하고 끝나면 `git worktree remove`"를 넣고 메인 체크아웃 경로를 함께 준다(developer.md의 worktree 절).
- 결과로 받은 에이전트 ID를 이슈별로 기억해 둔다. 같은 이슈에서 그 역할이 다시 필요하면 새로 띄우지 않고 SendMessage로 깨운다.

## 4. 질문 전달

에이전트 보고에 `[질문]`이 있으면:

1. 받는 역할이 기획·디자인·개발·QA면 그 에이전트에게 질문 블록만 전한다. 답을 받으면 새 에이전트를 띄우지 않고, 질문한 그 에이전트를 SendMessage로 깨워 답을 전하고 이어서 일하게 한다.
2. 질문과 답은 대화로만 끝내지 않는다. 오갈 때마다 이슈 회의록 댓글에 한 줄씩 남긴다(6장 형식).
3. 같은 질문이 두 번 오갔는데도 정리되지 않으면 PM 질문 목록에 넣는다.
4. 받는 역할이 PM이면 5장대로 처리한다. 막힘이 "아니오"인 질문은 일을 멈추지 않는다.

## 5. PM에게 묻기

묻기 전에 `docs/decisions.md`를 본다. 이미 정해진 것은 묻지 않고 그 결정을 따른다(출처를 회의록에 적는다). 되돌릴 수 있고 돈·법·약관·개인정보 공개 범위·범위 변경·승인 항목이 아니면 묻지 않고 팀장이 정한다: 기획에게 결정 로그 한 줄을 맡기고, 다음 PM 보고에 "팀장 결정"으로 사후 공유한다. 나머지는 단계가 끝나거나 막힌 질문이 생길 때 모아서 한 번에 묻는다.

```
#12 숙제 제출 — 결정이 필요한 것 2개
1. (질문) — A) … B) … → 추천 A: 이유 | 되돌릴 수 있음: 아니오 | 막히는 작업: #12 개발
2. (질문) — A) … B) … → 추천 B: 이유 | 되돌릴 수 있음: 예 | 막히는 작업: 없음
번호를 골라 답해 주세요. 답하지 않은 번호는 추천대로 진행합니다.
```

승인 항목(의존성 메이저 업그레이드, CI 변경, 운영 DB, 결제·정산 금액 계산 로직)은 "답이 없으면 진행하지 않음"이라고 따로 적는다.

## 6. 회의록과 마무리

- 에이전트 사이 `[질문]`과 답은 오갈 때마다, 그 밖의 진행은 단계가 끝날 때마다 이슈 회의록 댓글에 한 줄씩 남긴다.

```
회의록 — 디자인 단계
- 개발→디자인: 빈 숙제 목록 화면 → 일러스트 없이 안내 문구와 버튼 하나로 정리
- 기획→PM: 제출 마감 이후 재제출 허용 여부 → PM 답 대기
```

- 작업을 끝내기 전에 그 세션의 훅 차단 로그(`.claude/logs/*.jsonl`, 이슈 #17 6단계)를 작업 PR에 커밋한다. 클라우드는 세션이 끝나면 파일이 사라진다.
- QA가 실행 결과를 근거로 완료 조건을 모두 통과로 판정하면 PM에게 보고한다: PR 링크, 통과 수/전체 수, 남은 결정. merge는 PM이 한다.
- 하네스 PR(`harness` 라벨): 라벨을 붙일 때 PR head 커밋을 회의록에 적는다. 라벨은 그 뒤 push에도 남으므로, merge 요청 직전에 `git diff <그 커밋>..origin/<브랜치> --name-only`로 하네스 diff를 다시 보고, 라벨을 붙인 뒤 바뀐 하네스 파일이 있으면 PM 보고에 적는다.
